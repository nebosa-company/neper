e.ui.browser — migration tracker

Vaper (pure-Dart browser, frozen, never released) is being re-implemented in Neper as the e.ui.browser control, with every reusable piece (HTML/DOM, CSS style and layout, JS engine, network policy, decoders) placed in the general-purpose library and only browsing-context code in e.web.* (see “Library or browser?”). This page tracks (1) migration of what the Dart version already does, (2) gaps the Dart version never completed, which are built directly in Neper, and (3) core Neper language/stdlib work the browser needs. Dart will not be continued, so every gap is a Neper task.

Plan written 2026-10-16 · Dart baseline (REQUIREMENTS.md, last measured): 83/128 requirements (65%), WPT CSS reftests 116/122 (95%), html5lib 1549/1791 (86%), overall 78% · Dart size: ~48.5k lib LOC, ~44k test LOC, ~270 test files, 1.4k C (QuickJS shim).

Target architecture

Layers (bottom up)

e.ui.browser (lib/e/ui/browser.e) — one browsing context as a control: widget.Custom for paint, Region for pointer/wheel, Scope for keys/focus, Edit for text/IME/clipboard. Exposes navigate / history / find / zoom / events. Contains no engine logic.
e.web.page — browsing contexts, event loop (HTML processing model), navigation, session history + bfcache, iframes, workers.
e.js — JavaScript engine written in Neper: parser, bytecode, VM, own GC heap, builtins, ES-semantics RegExp, modules. e.web.bind — host-object bindings (DOM, CSSOM, fetch, timers, storage).
e.fmt.dom · e.fmt.css.style · e.fmt.css.layout · e.fmt.css.paint — arena node tables, style resolver, CSS box layout, display list lowered to e.gfx.scene.Builder.
Existing Neper libs reused — e.fmt.html, e.fmt.css.*, e.gfx.cssvalue, e.text.shape/layout/bidi/segment, image/font decoders, e.gfx.svg/filter/scene, e.net.* (http, tls, cookie, ws, idna, policy, ssrf), e.crypto.*, e.db, e.os, e.thread/channel.
x.web.* (drivers) — renderer process + OS sandbox, profile storage, credential store, platform keychains.

Threads and data flow

  • Engine thread owns DOM, JS heap, style, layout. Per-document arena + per-frame arena; nodes are indices into tables (no pointers across mutation).
  • UI thread runs e.ui.app; Custom.paint lowers the latest immutable display list to scene.Builder. Hand-off through e.channel, double-buffered arenas, tiled to the scene limits.
  • Net runs on e.task pool; responses arrive as events on the engine thread.
  • Later (P8) the engine thread moves into a sandboxed renderer process with the same display-list protocol over pipes/shared memory.
  • Dart's isolate boundary and RenderTreeSnapshot protocol (2.1k lines) are not ported; the in-process hand-off replaces it.

Key decisions (to be recorded as D-entries in docs/decisions.md)

#DecisionRationale / consequence
K1Three tiers, general-purpose first: reusable pieces go into the ordinary library (e.js, e.wasm, e.fmt.dom, e.fmt.css.style/layout/paint, e.net.*, e.text.*, e.ui.html_view); only what needs a browsing context stays in e.web.* (page, bindings, web APIs); only widget and input code is in e.ui.browser; platform/process code in x.web.*.Refines D5114 after the owner asked that reusable parts (WOFF, CSS, HTML, ...) benefit all library users. Test for “general”: it makes sense without a document that has an origin, scripts and a session history, and takes only data plus callbacks (measure text, load a resource). See the split table below. Mail HTML (C158), Document view (C172), help and Markdown can then share the layout engine without the browser.
K2Write the JS engine in Neper; do not embed QuickJS.Neper cannot link C objects or static archives with its own linker, cannot export symbols for callbacks, and the product claim is 100% self-hosted. D2148 already states this. QuickJS-ng in vaper/native stays a dev-time differential oracle only. This is the largest single cost in the plan (see P5).
K3All text goes through e.text.shape / e.text.layout; remove every dependency on dart:ui Paragraph.Removes Dart's biggest portability risk and allows vertical writing modes, which were blocked in Dart. Tests use the Ahem font as an asset for deterministic metrics.
K4Memory: arena per document and per frame; index-based DOM/box tables; the JS engine owns its heap and a mark-sweep GC over a byte arena.Neper has no GC and no global allocator. Index tables survive mutation and cross the thread hand-off cheaply.
K5Paint = Dart-style display list, lowered to e.gfx.scene.Builder in viewport tiles.The scene has hard limits (bounded SCENE_BYTES, MAX_EDGES per command, 8 clip masks, 4 opacity layers, TooLarge result). A full page cannot be one scene. Missing scene features (blend, backdrop read-back, glyph cache) are core tasks (track "core").
K6Freeze Vaper as an oracle, then stop touching it.Before retirement capture an offline site corpus, Dart render PNGs, node dumps and display-list dumps, and export test vectors as language-neutral fixtures (P0). Neper results are compared against these, not against a live Dart build.
K7Do not port: package:html wrapper, siphash/hkdf/chacha (Neper's e.crypto has vectors), Brotli and IDNA (exist), isolates, FFI, Flutter shell/render widgets.Each has a Neper equivalent or is Dart-specific.
K8Scope of the control: one browsing context. Tabs, omnibox, bookmarks, history, downloads and DevTools are an app layer on top (NeperOS Browser, C159, then a desktop shell).e.ui.app allows one window per app today; multi-window needs a core change or one process per window.
K9This page is hand-maintained and sits beside docs/progress.html.AGENTS.md makes progress.html the only readiness document and generated. This tracker is an explicit exception for one large programme; work is still sequenced through docs/work-queue.json items (a queue entry per milestone, referencing the IDs below). docs/vaper.md is superseded for layout, paint and JS.

Library or browser? The split

Rule of thumb, in order: (1) usable without a URL, origin, script realm or session history → general-purpose library; (2) needs only data and callbacks, no widget → library; (3) needs browsing-context state → e.web.*; (4) needs pixels, input or widgets → e.ui.*; (5) needs the OS (process, sandbox, keychain) → x.web.*. Public APIs of the library modules never mention “browser”, “tab” or “page”.

Practical consequence for ordering: M1 can ship e.ui.html_view (static page) before the browser control exists, and every layer below it is usable by other apps the day it lands. How to update this page

  • Edit the ITEMS array below: change a status and, when closing, put the commit or D-number in the notes. No generator; the page recomputes everything on load.
  • Status meanings: done verified against the named oracle; partial code exists in Neper but is unverified or incomplete; wip a session is on it; todo; blocked waits on another item; deferred deliberately out of the programme.
  • New work discovered while porting is appended as a new row, never silently folded into an old one.
