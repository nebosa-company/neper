# Looks: one widget set, several platform looks

Decided 2026-10-15 with the maintainer; decisions D5108 to D5113. Progress is tracked in `docs/ui/looks-progress.html`
(generated by `scripts/render_looks.py`; never hand-edited). Screenshots live in
`docs/ui/looks/<look>/<control>.png`.

## Looks

| Look | Profile | State |
|---|---|---|
| Neper | `Neper` | the existing default; every control is the baseline |
| Windows | `Windows` (+ a dark palette for the button) | the MTG Studio v3 look: DevExpress VCL controls on a flat, native-style Windows face. Replaces the working name MtgStudioV3 |
| macOS / iOS | `CupertinoLike` | later; column kept in the matrix, marked planned |
| Android | `MaterialLike` | later; column kept in the matrix, marked planned |

## Mechanism

- A look is a `ThemeTokens` built by `style.reference(palette)` plus a profile-specific builder
  (`style.windows(palette)`), and, where a control's shape differs and not only its colours or
  metrics, a branch on `t.tokens.profile` inside that control. The data grid keeps its own `Look`
  (`e.ui.gridlook`); the Windows grid look is `gridlook.v3()`.
- One widget set. No second control library per platform.
- The Windows look is measured, not invented: the reference is the DevExpress VCL control as
  MTG Studio v3 draws it (mostly `lfFlat` with `NativeStyle`, some `lfOffice11`; no global skin),
  recorded in `docs/grid-parity/` and in `docs/ui/looks/ref/windows/`.

## Screenshots without a display

`e.ui.looks` renders offscreen on the CPU backend and writes PNGs with `e.fmt.png`; no window, mouse or
keyboard. Each control has a sheet app `examples/looks/<control>.e` (45 in all, some extra `_dialog` and
`_states` sheets composed like the captures); `scripts/render_looks_all.sh` renders them all. The v3 reference
is captured live from a launched copy of v3 by posted window messages (`scripts/grab_v3_*.ps1`, output in
`docs/ui/looks/ref/windows/`, about 250 captures); hover cannot be captured. How-to and safety rules:
`docs/ui/looks-howto.md`.

## Control matrix (Delphi / DevExpress -> Neper)

label (TcxLabel), button (TcxButton), checkbox (TcxCheckBox), radio (TcxRadioButton), radio group,
text edit (TcxTextEdit), spin edit, combo box, image combo box, date edit, mask edit, memo, button
edit, token edit, check list box, progress bar, group box, page control (tabs), splitter, status
bar, toolbar button (TdxBarButton), menu bar, popup menu, hint (tooltip), scroll bar, list box,
tree list, vertical grid (property grid), data grid, dialog (form chrome). Gaps with no Neper
control yet (embedded browser, chart, tray icon, native file dialogs) are listed, not built.

## Order of work and where it stands (audit 2, 2026-10-16)

1. Core: `Profile.Windows`, `style.windows`, the harness, the progress page. Done.
2. v3 reference captures: done for rest, pressed, focused and open states; hover pending (optional
   GetCursorPos hook). `date_edit`, `memo`, `token_edit`, `progress_bar` and `hint` have no v3 capture.
3. Controls in parallel through status overlays (`status.d/`, one file per worker or round).
4. Per control: measure, implement, render beside the capture, record. Statuses are `planned`, `started`,
   `review`, `matched` (every captured state has a cell within tolerance at 100 %) and `ready` (also at 150 %).
   The independent audit (`docs/ui/looks/audit.md`) decides: today 0 matched, 0 ready, 25 review, 5 started.
5. In flight: hover captures and round 5 matching. Known weaknesses: baked ring and edit tiles dotted at
   1.5x, open-list sheets, data grid, 81 of 200 captured states without a sheet cell. Cupertino and Material
   stay planned.
