Ten languages, one window: what you install

October 23, 2026 · Neper binaries measured with emit-executable; every other number is cited below

Putting one window on screen on Windows, Linux and macOS takes very different amounts of software depending on the language. We read the official install guides for ten popular desktop languages and set them beside Neper. Neper wins on three things: one install builds Windows and Linux programs from a single machine, the user installs nothing to run them, and the window is 2.7 MiB with no runtime inside it.

Where Neper wins

  • One install, several targets. Windows, Linux and macOS executables, for x64 and arm64, came out of one Windows machine with one compiler, one command each. The ten others mostly build each OS's package on that OS: jpackage, PyInstaller, Compose and Tauri's MSI all say so, and Flutter needs Xcode on a Mac and Visual Studio on Windows.
  • No second toolchain. The compiler writes the PE and ELF files itself, with its own linker. No SDK, no Visual Studio workload, no clang, no -dev packages, no MinGW. Seven of the ten need a C++ toolchain somewhere (see below); for Neper it appears once, to build the first compiler.
  • Nothing to install to run. No .NET or Java runtime, no VC++ redistributable, no Qt or GTK libraries, no bundled browser or interpreter. On Windows the program calls the system's own window functions. On Linux it speaks the X11 protocol itself. On macOS it uses the frameworks that ship with the system.
  • Small, with everything in it. A window with the real renderer and widget runtime is 2.7 MiB on Windows and 2.8 MiB on Linux. That is below every reported size in the tables that follow: Electron 115 to 151 MB for the runtime alone, Compose about 50 MB, Qt 42 to 50 MB, Flutter about 25 MB, Wails 8 to 11 MB and Tauri 3 to 5 MB. Only Tauri's own documentation claims less (under 0.6 MB), and that number leaves out the system webview.
  • No IDE, no installer. Edit in anything, build from the command line. There is no designer to buy or workload to select.

The rest of the post is the evidence: how we picked the ten, what each of them needs, and how Neper's numbers were measured.

How we picked, and what we counted

No 2025 or 2026 survey measures which language people use for desktop. We took language usage from the Stack Overflow 2025 survey and desktop frameworks from its 2024 edition, the latest that asks: .NET 25.2%, Flutter 9.4%, Qt 7.3%, Electron 6.5%, SwiftUI 4.3%, Tauri 2.4%. The ten are C#/.NET, C++, Java, JavaScript/TypeScript, Python, Kotlin, Dart, Rust, Go and Swift. Kotlin is the weakest pick: Compose Multiplatform is not in the 2024 framework list. Delphi (2.5% usage) is the likely swap for someone ranking desktop only. We could not verify that, so we kept the list.

For each language we took its mainstream cross-platform path, plus the native path where that is what people use, and counted three things:

  • To build: what you install on the developer machine to get an executable, including anything the language's own installer does not cover, such as a C++ workload or Xcode.
  • To run: what the end user must already have, or what the app must bundle.
  • The smallest app: a hello window, when a source gives a number.

Two kinds of numbers appear. Neper's are ours: we built the programs and read the file sizes. Everyone else's are from official documentation or vendor download metadata, which we mark, or from third-party reports, which we mark "reported". We did not build a hello window in the other ten. Cells we could not source say so.

What the ten have in common

  • Seven of the ten reach a C++ toolchain on at least one OS. C++ itself, Flutter, Rust, Fyne, Swift on Windows, Tauri and .NET Native AOT all do. On Windows that means Visual Studio or its Build Tools, which Microsoft lists at 2.3 to 60 GB.
  • The managed languages move the weight to the user's machine or into your package. .NET and Java need a runtime unless you bundle one. Electron bundles a browser. PyInstaller bundles an interpreter.
  • You build each OS on that OS. jpackage, PyInstaller, Compose and Tauri's MSI all build their packages natively. Cross-compiling a desktop app is the exception, not the rule.
  • The IDE is rarely required. Every language here builds from a command line. The exceptions are in practice: Xcode for Swift on macOS, and Visual Studio as a toolchain for Flutter and C++ on Windows.

Neper

Neper's compiler writes the executable itself, including the PE, ELF and Mach-O headers, the linker and the ad-hoc macOS code signature, so a program does not go through a C++ compiler, an SDK or a system linker. The compiler is written in Neper. Getting the first compiler means building from source, and that is the one place a C toolchain appears:

$ scripts/build-selfhost.sh   # Linux, macOS; scripts/build-selfhost.ps1 on Windows
# a throwaway C99 bootstrap (cl, or cc) builds the compiler once;
# the compiler then builds itself and prints its own path

After that the C compiler is not used again. We built the repository's smallest window program, ui_app (a 200 by 120 box, built with the real window, renderer and widget runtime), and a console hello, from one Windows machine with the self-hosted compiler:

$ neper-self emit-executable tests/selfhost/fixtures/link/ui_app/src/main.e . x64 windows hello-win.exe --release
$ neper-self emit-executable tests/selfhost/fixtures/link/ui_app/src/main.e . x64 linux   hello-linux --release
$ neper-self emit-executable tests/selfhost/fixtures/link/ui_app/src/main.e . aarch64 macos hello-macos --release
$ neper-self emit-executable examples/hello.e . x64 windows h.exe --release   # also: x64 linux, aarch64 linux, x64 macos, aarch64 macos

In the form of the two tables above:

  • To build: the Neper compiler and a text editor. No SDK, no IDE, no installer download, and no second language's toolchain once you have the compiler.
  • To run on Windows: Windows. The program calls the system's own window functions.
  • To run on Linux: a display with an X11 socket. Neper speaks the X11 protocol itself, with no GTK or Qt. XWayland works; a Wayland-only session does not.
  • To run on macOS: macOS. The program uses the Objective-C runtime, CoreFoundation and CoreGraphics that ship with the system.
Size is not a clean win.

At 2.7 MiB the window is smaller than every reported figure above, including Tauri's 3 to 5 MB benchmark, but Tauri's own documentation claims under 0.6 MB, and its webview is not counted in that number. Neper's size is the whole window stack: the CPU renderer and the widget runtime, because Neper draws its own pixels instead of using native widgets. A console program is 12.3 KiB.

The limits of those wins

  • No Wayland. A Linux session without an X server cannot open a window. window_open answers Unsupported.
  • macOS builds from Windows, but we have not run those binaries on a Mac. The x64 and arm64 executables are real Mach-O files, ad-hoc signed by the compiler as Apple Silicon requires. The repository's runner checks (a macos-14 machine, x64 under Rosetta) cover the console and system-library side; the window program is built here but not confirmed on a Mac. There are no .app bundles, no Developer ID signing and no notarization, so a Mac app for other people still needs an Apple Developer account and a manual bundle step, in any language.
  • No packaging story yet. There is no MSI, DMG or deb builder, no installer, and no package-manager release of the compiler. Today you clone the repository and run the build script.
  • Windows still needs a C toolchain once. The bootstrap builds with cl, so the first compiler on Windows needs the MSVC build tools. This is the same prerequisite as Rust, Flutter and C++ have, paid once instead of per project.
  • No designer, and a young ecosystem. There is no visual designer, no third-party control market and no Stack Overflow answer history. Every library in the box is Neper's own.
  • This is not a like-for-like size test. The other ten rows are sourced reports of different app shapes (a console app, a template, a forum post). Only the Neper rows are ours. Build the same hello window in each language and measure it before quoting any ratio.

Targets we plan next

The compiler's target list is shorter than the one above suggests. What exists today is Windows, Linux and macOS on x64 and arm64. These are planned, and none of them exists yet:

  • Android, on x86_64 and AArch64. The design document describes a distinct Android target, not an alias for Linux. The aim is to write the APK itself (binary manifest, aligned native library, signature) with no Android Studio, SDK, NDK, Gradle or Java.
  • iOS. The first step is compiling to arm64 iOS Mach-O objects on Windows. The final link, app bundle, signing and upload would stay in Apple's own toolchain, because iOS has no unsigned path: it needs an App ID, provisioning profile and entitlements. So "nothing to install" holds for compiling, not for shipping to the App Store. The language specification currently excludes iOS.
  • WebAssembly. Today Neper can run WebAssembly: e.wasm is an interpreter for the 2.0 core format. Compiling Neper programs to WebAssembly is a goal with no design document yet.

FreeBSD is evaluated as a candidate and not scheduled. Each of these is a distinct target with its own binary rules, not a relabelled Linux or macOS build, and we will report them here as we measure them, not before.
